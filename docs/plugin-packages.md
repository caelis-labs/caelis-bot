# Bot plugin packages and directory adapter

Bot loads [Agent Plugins 1.0 portable packages](https://agent-plugins.org/specification): root `plugin.json`, optional `skills/<name>/SKILL.md`, and optional root `mcp.json`. Package resources and executable CLI files can be carried in the verified inventory. Bot does not run lifecycle hooks or install scripts. A plugin contributes Skills and MCP servers only to the persistent Bot owner; Workers retain their own runtime configuration.

The production source remains the build-owned, SHA-256 reviewed catalog in `internal/plugins`. Adding a package requires a vetted inventory and a Bot release. Installation and activation are separate from reading a listing. The installer verifies every file, rejects unexpected paths and symlinks, and stages immutable package bytes before Runtime projection. On POSIX hosts, reviewed executable file modes are retained; nonexecutables cannot silently gain execute permission in the private installed copy.

`NormalizeMarketplace`/`OpenReviewedMarketplace` are an offline source adapter for the documented [Codex local marketplace `marketplace.json`](https://developers.openai.com/plugins/build/plugins#marketplace-metadata) form: `plugins[].name`, `source: {source: "local", path: "./..."}`, policy, and optional `interface.displayName`. The adapter reads portable packages from a supplied filesystem, verifies a separately approved hash inventory for every byte, then feeds the same Bot manager. Two different packages can be listed and installed without page-specific code. The index alone does not confer trust or install permission; `INSTALLED_BY_DEFAULT` is never automatically applied. Git and arbitrary URL sources need a separate pinned fetch, review, and distribution owner before they can be exposed in Settings. Bot does not register these packages in Codex's global or user marketplace.

| Surface | Current support |
| --- | --- |
| Portable package identity and publisher | Verified `plugin.json` `name`, `version`, description and `author`; optional reviewed display text. |
| Skills | Verified metadata in snapshots; bounded, sanitized body read only when details open. |
| MCP service directory | Service names from verified `mcp.json`. The private index uses only the selected resident Runtime's connected status; an explicit detail view may independently preview a not-yet-started service. |
| Codex tool directory | Private resident thread's public `mcpServerStatus/list`, narrowed by `serverName` and `toolsAndAuthOnly`; names, descriptions and present annotations are displayed. |
| Core tool directory | Released v0.68.0 public `mcp-status` reports ready/failed state and tool names. When a newer Core includes optional `tool_details`, Bot matches descriptions to those ready names; missing descriptions remain absent. |
| Connection actions | Reviewed API-key and token declarations support write-only save, edit and clear in Bot's private local credential store. Each plugin revision has an independent file in the `Credentials/plugins/` namespace; existing Keychain items migrate on first use and are removed. An unconfigured server is omitted from Runtime selection. A versioned Bot stdio bridge injects the credential into the upstream environment, HTTP header or URL query at execution time. Settings shows saved configuration separately from resident Runtime health. |
| OpenAI hosted connector mappings | `.app.json`, registered connector IDs and OpenAI-hosted OAuth are outside portable package activation. They are not imported or represented as Bot connections. |

Tool annotations are server claims, not permission grants. Discovery never invokes `tools/call`; built-in automatic approvals remain scoped to the existing built-in services. The detail cache is bounded to 32 entries and 15 seconds, keyed by Bot catalog revision, package version, Runtime connection generation and service identity. Refresh bypasses it. A successful independent detail probe is marked as a preview and does not change the Runtime's not-started state. Settings calls an installed and enabled package “Enabled”; only the detail view reports Runtime connection health. Disabled or uninstalled services are answered locally without Runtime discovery.

The resident-only `app-skills/mcp-tools.json` is a plain file of package/service ownership and actual tool names and available descriptions. It is rebuilt from selected services only after the active Runtime reports them connected, using that Runtime's status metadata without a separate per-turn MCP connection. This is the Runtime's connected tool directory, including tools that ToolSearch has not yet loaded into the current model request. Failed, disabled and unknown services disappear. Equal content is not rewritten. The file contains no schema, tokens or tool results, is not injected into the default prompt, and is never copied to Worker roots. `bot-core` points the resident Bot to it conditionally; the Runtime's own ToolSearch still owns schema loading and invocation admission. Plugin Skill names and descriptions continue through the Runtime's existing Skill discovery, with bodies loaded on demand.

Dream renewal creates a new Codex thread or Core application session while retaining the Bot host's plugin selection, connection authorization and original operation receipts. This is the existing context replacement boundary; Bot does not replay calls or rebuild Runtime visibility from old search history. Released Core v0.68.0 includes native ToolSearch: the new session starts without schemas loaded by the retired session and discovers ready tools through its own Runtime. Codex starts a new thread instead of resuming the old rollout. Core's `mcp-status` reads the connected MCP Manager directory independently of model visibility. On a cold Core session, status can be inactive until the first turn assembles the manager, so the index may be empty during that turn; Bot refreshes it after the turn when the service is connected. Both adapters' fresh-session requests have protocol fixtures; a native end-to-end search, Dream renewal and new-session first request remains an acceptance check.
The persisted `caelis-dream` handoff marker remains a storage compatibility marker for already submitted legacy attempts. New installations retire the `bot-dream` Skill; a matching legacy handoff can migrate into APP-private storage without deleting the Notebook file.

The bundled first set is Brave Search (official npm `2.1.4`, vendored with scripts disabled), GitHub's hosted read-only default toolset, Notion's hosted server, Obsidian Local REST API's built-in MCP endpoint, Amap's hosted MCP endpoint, and Tencent Docs' hosted endpoint. Only the verified portable descriptor and bundled Brave artifact are pinned. Hosted servers are operated and updated by their publishers; their service implementation cannot be byte-pinned by Bot. Markdown writing leaves Browse but an existing installed copy remains recoverable and removable.

The HTTP bridge forwards Streamable HTTP JSON-RPC requests and SSE responses without retrying an unknown `tools/call`. It blocks redirects so credentials cannot follow a changed host, caps response size, and returns generic authentication/network errors without upstream response bodies. Obsidian can trust a user-supplied PEM CA only for its own MCP transport; system TLS verification stays enabled. Its community plugin must already be running. Brave requires Node.js 22 or newer on the local machine. The catalog never runs npm, install hooks or upstream setup scripts at install time.

Notion's hosted server uses interactive OAuth with PKCE and dynamic client registration. Bot discovers resource and authorization metadata, opens a loopback callback for browser consent, and keeps client identity and tokens in its native private store. A signed-in user chooses the workspace in Notion. A successful callback applies a new connection revision under Runtime admission; failed or cancelled authorization does not enable the server. Refresh is serialized across relay processes and never replays an MCP call with an unknown outcome. Real account consent and tool behavior still require user acceptance. GitHub currently accepts an explicit user PAT for the hosted MCP endpoint; it does not inherit Codex login or claim GitHub OAuth. Credential-backed services require the user's own key or token and remain unconfigured until one is saved. The Tencent Docs Authorization value is sent exactly as entered, following the publisher's guide; GitHub and Obsidian use `Bearer`. No secret enters Core profiles, Codex project config, snapshots or desktop metadata. OpenAI-hosted OAuth and connector IDs remain separate.
