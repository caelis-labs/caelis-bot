# 已确认问题修复清单

2026-09-25 更新。本清单记录修复、复现依据和验证边界；本地改动尚未发布。

## CHAT-01：发送后用户消息延迟出现，等待圆点先出现

- [x] 实现修复并通过回归。
- 现象：提交用户输入后，聊天先显示 Bot 的等待圆点，用户消息稍后才出现。
- 原因：`frontend/src/Panel.tsx` 的 Composer 提交时不添加待发送消息，聊天依赖后端
  `userMessage` 投影；Codex adapter 在等待 `turn/start` 回执前已发布 `sending`，
  `chatActivity` 据此显示圆点。450 ms 的快照轮询还会增加显示延迟。
- 已验证：修复前的临时 Go overlay 用例阻塞发送回执，生产 Session 快照为 `phase=sending`，
  用户消息数仍为 0。此处是修复前证据，不代表当前实现。
- 修复方向：提交时立即显示带发送状态的用户消息，以稳定请求标识与原生回执/消息合并；
  明确区分发送中、已接受、拒绝和结果未知，不以本地显示冒充后端接受。
- 验收：慢回执时用户消息先于等待圆点可见；接受后不重复、不闪退；拒绝或未知时可理解、
  保留草稿且不自动重发；覆盖普通消息、附件和运行中补充，以及聊天/快捷输入表面切换。

## CHAT-02：worker 已完成后仍显示忙碌和停止按钮

- [x] 实现修复并通过回归。
- 现象：主对话与两个 worker 均有真实完成记录，聊天仍显示等待圆点和停止按钮。
- 已验证：本机原生记录确认本次两个子回合与主回合均已完成。当前日志未保留原始 App Server
  通知顺序，不能据此声称完整重建了现场事件顺序。
- 可复现缺陷：`internal/backend/codex/bot.go` 的 `childEvent` 收到子回合
  `turn/completed` 后删除活动记录；若随后收到主回合的 `subAgentActivity(kind=completed)`，
  `trackWorkerActivity` 又写入空 run 的 `childRuns` 条目，并因 `childWatching=true`
  直接返回。`Session.update` 因残留条目将完成状态改回 `working`。
- 修复前临时 Go overlay 用例固定两种顺序：先活动通知、后子回合终态时正常；先子回合终态、
  后活动通知时得到 `working / canSend=false / canInterrupt=true`，完成态断言失败。
- 修复方向：原生回合终态不能被无回合标识的迟到活动通知重新激活；必要的只读核对应与
  长期订阅状态分开，仍保留真正的新回合和未知结果，不根据助手文本推断完成。
- 验收：覆盖两种事件顺序、重复完成通知、订阅恢复与新回合；主回合和全部相关子回合结束后
  消除虚假忙碌、恢复输入与角色空闲，真正运行中的 worker 和审批仍受正确管理。

## 关联调查：本次 worker 为什么没有脚底终端入口

本次模型调用的是 Codex 原生 `spawn_agent` / `wait_agent`，未调用 Bot 的 `bot_task_start`。
两个子代理各有独立 thread、原生父子关系及完成记录，但共用 Bot 的 Notebook 工作目录；
不属于 Bot 创建的独立 `Tasks/<handle>` 工作任务。

本机记录仅包含 native `children`，adapter 的受管任务集合与 `tasks.json` 产品账本均为空。
`WorkStates` 只导出受管任务，`TaskPreviews` 只从产品账本生成脚底入口，`WorkTerminal`
也要求受管任务绑定。因此这次没有脚底入口，不能解释为任务太快完成或没有真实执行。
此外，当前原生 UI 在聊天窗口获得焦点时会暂时隐藏任务入口；这与账本为空是独立条件。

现有产品约定要求专业工作经 Bot 自有任务接口进入受管目录。后续需要核对秘书工具暴露与
委派约束为何仍允许走原生子代理路径；本轮只记录调查结果，未改变委派策略或接管已有线程。
