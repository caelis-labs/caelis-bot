## 交付原则

前期已用火柴人验证宿主和真实工作，现已接入小爱。下一步推进可用性收尾，同时将基础
3D 表现力与 Desktop/Dock/ActiveWindow 轻量骨架纳入近期主线；独立道具、随机待机和互动同时定义，
再扩展复杂任务/窗口关联。不再将基础动作与创作工具一并后置，初期以开发者自用和有辨识度的演示验收。
使用 Wails/Go + React/TypeScript + Three.js；角色资产走 Blender → GLB。
Codex App Server 为第一个后端；Caelis 已替换为通用应用 adapter；当前接入范围见 [接入说明](caelis-integration.md)。协议保留充分能力，用户入口保持克制。

每个阶段交付可独立验证的增量，不按预计天数承诺。原生透明交互和后端恢复属于需要
实测的风险点；用结果决定下一步，不以演示截图替代行为验证。

## P1 — 状态栏与火柴人桌宠

目标：不用普通主窗口，用户依然能找到、移动、缩放、隐藏和唤回 Caelis Bot。

2026-09-19 进度：P1.1–P1.4 已实现，单屏 Retina 的拖动、穿透、焦点、尺寸和生命周期
已有实机证据。用户已明确确认真实鼠标可拖动、透明区域可点击下方应用。
输入入口按用户选定参考图改为 Bot 下方胶囊；左侧“+”仅展开附件，P2 已加入真实可用的技能/插件技能引用；设置窗口内连续调节尺寸，
点击外部收起，无独立关闭按钮。P1 当时仅有本地选择；P2 已实现发送时复制、校验与原生输入映射。
P1.5 的显示回收逻辑已有测试；原生全屏从旧“不跟随”策略改为保持显示，并已补验；多屏热插拔、
睡眠恢复和完整 GPU/功耗数据尚未实测。**P1 不标记为全场景验收完成。** 用户已确认切桌面后的
拖动、点击与穿透回归通过；检查点 `a4cc357` 后按授权推进 P2.1，未测硬件场景保留为发行门槛。
详细方法和限制见[原生验收](native-acceptance.md)。

跨平台在 P1 固定[实现基线](platform-baseline.md)：macOS/Windows 共享核心编译守卫加入 `make check`，
当前只实施 macOS，完整发行后再实现 Windows；Linux 暂不列入计划。
Windows 只保留接口扩展和编译守卫，不以共享编译通过提前标记平台完成。

| 增量 | 实现范围 | 可验收结果 |
| --- | --- | --- |
| P1.1 生命周期 | 状态栏、显示/隐藏、明确退出；关闭最后一个面板后继续常驻；验证 accessory/Dock 行为 | 冷启动不弹旧欢迎窗；无面板时仍能从状态栏唤回；退出能完整回收进程 |
| P1.2 占位渲染 | 最简单的火柴人 GLB；透明无边框宠物窗口；Three.js 渲染与资源释放 | 真实桌面 GPU 可见；背景透明；仅必要的本地 idle/交互反馈；无模型调用 |
| P1.3 几何与输入 | 等比缩放、拖动、位置/比例持久化；OS 命中/穿透与焦点策略 | 角色可拖动；周围透明区不挡桌面；缩放后命中与视觉一致；输入时才获取键盘焦点 |
| P1.4 轻量入口 | 宠物旁紧凑唤起入口、可收起的输入/结果面板骨架；最少偏好 | 不出现 Session、工作区树或常驻工作台；未接后端时不伪造发送成功 |
| P1.5 桌面适应性 | Retina、多屏、移除显示器、Space/全屏、睡眠恢复、隐藏时暂停绘制 | 宠物不会永久丢在屏幕外；显示恢复可用；记录实际支持范围与空闲成本 |

实施顺序：先用最简窗口验证 P1.1 的常驻/焦点，再完成 P1.2–P1.3 的渲染和交互，
最后增加 P1.4 的面板及 P1.5 验收。占位火柴人可程序生成，只需可复现导出和少量
基础反馈，不建立正式骨架规范，不开展原创角色设计。

P1 原生验收至少覆盖：

- 冷启动、再次唤起、收起所有面板、隐藏/恢复宠物、明确退出。
- 宠物拖动与点击不会意外抢占其他应用键盘；输入面板可输入中文并在收起后归还焦点。
- 缩放最小/默认/最大值后，角色、窗口、面板锚点、命中区域同时正确；重启恢复偏好。
- 在透明区域点击下方应用确实收到事件。Three.js raycast 结果不能代替此验证。
- 可用硬件上的多屏/DPI/移除屏幕、Space/全屏和休眠恢复；无法实测的场景单独标记。
- 记录机器、占位资产、空闲/交互帧率及 CPU/GPU 基线；隐藏时停止不必要渲染。

局部穿透若受 Wails 版本限制，先做可重现的原生实验；必要时隔离小型 AppKit 桥接。
整体透明窗口可用不等于局部穿透已成立；不得为了过关把整块矩形默默变成输入遮罩。
性能预算在真实机器首次测量后确定，本计划不编造未经验证的数字。

P1 完成时保存实机截图/检查记录，更新准备状态。它证明桌面宿主，不证明 Agent 可用。

## P2 — Codex 真实工作闭环

目标：用户通过桌宠说出需求、补充附件、作出审批，得到真实结果，全程不管理 Session。
依赖 P1 窗口生命周期成立；当时使用火柴人，当前角色接入见 P4.1。

2026-09-19 进度：P2.1–P2.5 核心路径已实现并连接原生输入、实时气泡内审批和可选 IM 聊天窗口。真实 Codex 0.153.4
已验证对话、文件附件读取与产物、命令审批、中断、后台工具退出清理和重连历史。
原生对话与审批也有实测；不以 CLI 验证替代全部 UI 路径。仍需补验干净账户登录、
外部插件/MCP 授权、挂起/网络故障及长任务恢复。具体证据与限制见
[backend-acceptance.md](backend-acceptance.md)，不把 P2 全能力或发行验收标记为完成。

| 增量 | 实现范围 | 必须保留的语义 |
| --- | --- | --- |
| P2.1 传输与身份 | 固定版本原生 schema；自有 app-server 子进程、stdio、initialize、鉴权状态、请求路由 | 请求关联、原生错误、退出/断线、超时后结果可能未知；不接管不属于本应用的进程 |
| P2.2 内部契约 | command/event/snapshot/capability 映射；创建/恢复内部对话绑定 | backend instance、conversation、run、item 与 request 身份；前端不需要展示这些 ID |
| P2.3 最小对话 | 输入、流式输出、真实工具进度、结果/产物、中断；支持时才提供补充指令 | 终态明确；当前任务目标准确；历史重建不等于重新执行 |
| P2.4 附件与审批 | 文件选择/拖入、类型与大小校验、原生输入映射；有上下文的审批与结果回执 | 区分路径引用与真实上传；准确绑定请求/选项；失效、拒绝、重复点击和另端解决都可处理 |
| P2.5 恢复与后台 | 重连重建、挂起/恢复、关闭面板、明确退出、重启观察策略 | 不自动重发结果未知的写操作；不通过动画推断成功；不把中断说成完成 |

`internal/backend/api/contract.go` 是宿主到 renderer 的唯一类型来源；
`cmd/contract-gen` 生成 `frontend/src/backend/contract.ts`，`make check` 检查漂移。
Go 服务持有文件、原生请求及进程，UI 只消费投影。56 份已消费 native JSON schema
与哈希随 adapter 纳入仓库，分别记录稳定/experimental 来源；`make schema` 从锁定
binary 重新生成对比。Session 客户端启用 experimental API 以使用后台终端清理等字段；
不因启用能力标志就默认接受未知请求。

附件能力按实际支持类型提供：图片、普通文件路径、可上传文件等不能相互假装等价。
不支持的类型及时解释并提供可行路径。审批必须展示实际动作对象及选项，宠物互动
不作为批准。并发任务即便没有标签页，也必须在内部正确路由，不能串审批或中断目标。

测试分三层：

1. 可重复的协议 fixture/契约测试：流式合并、native mapping、乱序/重复事件、请求
   关联、过期审批、断线后的未知结果；故障由传输模拟触发，不靠 sleep 掩盖竞态。
2. 本机真实 App Server：验证鉴权状态、真实工具调用及一次需要审批的工作，在专用
   临时目录产生并检查结果；观察中断/恢复。真实调用与离线 fixture 结论分开记录。
3. 原生端到端：从桌宠入口完成输入、附件、审批、查看结果；隐藏面板后执行语义保持
   一致；明确退出不留下无人管理的子进程。私密输入与凭据不进入仓库测试资料。

P2 验收场景应是普通用户的目标，例如“根据这个附件整理一份摘要，并保存到我选择
的位置”。用户只需要理解需求、授权和结果，不需要知道后台线程、协议或工作区。
审批场景须按后端真实策略构造，不能添加与真实执行脱节的假确认框。

### P2 Bot 语义增量（2026-09-19）

已实现同一 Bot 身份、无新会话/工作区入口；共享草稿；三表面统一系统主题；输入仅用于
空闲发送、气泡最新回复/原位审批/停止/确认、聊天接近 IM。增加常驻本地调度器和 3 项
自有 MCP 工具；默认 auto_review，自有工具逐项批准并渐进发现。真实恢复后调用、
到期唤醒与双 worker/通信已通过；完整分层证据见 bot-design.md 和 backend-acceptance.md。
不将真实硬件睡眠、所有 worker 故障恢复或正式角色动画标记为完成。

## P3 — 普通用户的可用性

首版收敛顺序与剩余工作见 [MVP 清单](mvp-checklist.md)。当前推进本机发现/登录恢复、
自动审查结果和系统通知；历史分页、附件副本清理和脱敏诊断已接入。稳定协议以固定 schema 和边界测试为准，只有未确定的原生
行为做针对性实测。首版不追求覆盖全部极端故障组合。

在真实能力基础上补齐首次使用、登录/连接、清晰错误恢复、少量偏好、安装与更新。
按工作需要展开插件/连接器安装和授权，明确支持状态、身份和权限，操作后查询真实
结果；不提前堆出完整管理后台。没有可用能力时不显示虚假入口。

早期 pre-release 使用 ad-hoc ZIP + SHA-256，README 已明确 Codex 发现/安装与协议兼容、
单应用信任放行、手动更新和数据保留。按用户决定暂不以 Developer ID/公证阻塞早期预发布；
这两项留到完整发行。最终用户不需要 Node、Go 或 Blender，Blender 留在创作者工具链。

验收：新用户能理解“如何开始、现在在做什么、哪里需要我决定、结果在哪里”。
后端不可用和账户失效时可恢复；用户可以安静地隐藏宠物且不会失去入口。

## P4 — 角色表现与桌面行为

当前采用 Caelis 成品，制作工作迁入私有资产库。主项目负责五段 clips、六套本地待机、
鼠标/工作回应、表情/手指/视角修正、拖动跑步和独立道具。技术接入不代表视觉自然度已验收。
继续以开发者日常自用和真实演示为目标，复杂空间理解、通用重定向和市场后置。
多角色/服装先用版本化成品合同交接，再按产品需求提供选择界面；见 [成品合同](character-assets.md)。

## 本地开发与交接纪律

原生 Run 入口为 `script/build_and_run.sh`；纯前端预览不能验收桌面行为。
运行受影响的 `make check` / `make smoke` / `make build`，协议与生命周期的改动应补充
有意义的行为测试。新依赖按需添加、固定版本并保留锁文件。
每阶段同步更新实际状态、验收证据和剩余限制；提交与推送分别取得用户授权。
下一实现范围按[路线](roadmap.md)的 A/B/C 顺序收敛：P3 可用性收尾与 P4.2 基础表现力均为近期，

交接入口见 [handoff.md](handoff.md)，实际验证与未测范围见 [准备状态](preparation-status.md)。
