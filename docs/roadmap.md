# 产品发展路线

更新：2026-09-20。根据用户对「桌面智能体深度研究」的讨论与本轮反馈确定。
本文件记录产品方向、阶段顺序和竞争力假设；不将研究建议自动视为已实现能力。
本轮仅持久化文档，不修改程序、角色资产，不新增提交或发布授权。

## 产品目标

Caelis Bot 是具有持续身份、能接受委托并在桌面上作出情境化反应的个人助手。
用户始终面对同一个 Bot，通过自然语言交代事情、提供材料、作出必要决定、取得结果。
桌面角色是可交互的身体；对话、工具和后台 Thread 是完成委托的能力。

早期就建立 Desktop、Dock、ActiveWindow 的轻量概念骨架，驱动情境动作和独立道具；
复杂桌面语义与任务空间理解后置。长期由 Agent 驱动角色观察、转身、靠近、等待、提醒和交付。
角色的行为应帮助用户理解发生了什么，并具有自己的表达方式。
只有模型变成 3D、聊天入口换成宠物、工作时播放循环动画，尚不足以达到这个目标。

保持面向普通用户的定位。已有 Codex 的开发者可以作为早期试用人群和长任务验证者，
初期以开发者持续自用和有辨识度的真实演示为主要目标，不急于证明普通用户长期留存。
不因此将产品改为 Coding 工作台或多个 Agent 的监控面板。默认一个 Bot 对用户负责；
后台多个工作 Thread 不自动变成多个角色、标签页或可见 Session。

## 当前判断：接入成立，表现力和竞争力尚未成立

原阶段基线为 `c50d6d4`。真实 Codex 工作流、长期 Bot、常驻提醒和小爱 v0.4.1 已接入。
角色有 idle、working、attention、nod、celebrate 五段动画和过渡，使用固定正交视角；
该基线尚无情境注视、主动转身、空间移动、窗口关联和统一行为调度层。

本轮 P4.2 已开始实现：复用原 Blender/GLB/骨架和渲染参数，增加平滑混合、头部先行/身体跟随、
六套待机组合、轻量环境快照及独立飞机。自然流畅、轻盈和可辨识互动优先于模型细节精修；
精修仍是正式发布前工作。当前进度不等于 B 已通过自用/演示或竞争力验证，见[实施记录](preparation-status.md#2026-09-20p42-首个行为与道具切面)。

用户本轮反馈是「几乎没有动作，体现不出 3D 优势；小尺寸精细度观感不如 2D Codex Pet」。
这是产品体验缺口。单张截图不能诊断动画是否停播，已有片段/状态测试也不能推翻该反馈。
后续先检查实际播放可见性、姿态差异、动作幅度和触发时机，不直接归因于模型面数或帧率。

**五段 clips 能播放只是资产接入验收，不是角色表现力验收，更不是产品竞争力验收。**
基础动作与空间表现从原先笼统后置的「美术线」提升为近期产品主线；复杂动作库、角色市场、
通用重定向和创作工具仍后置。不重复人物建模，不修改原交付包来掩盖宿主表达问题。

## 竞争力假设与验证

参考产品已经覆盖桌面输入、任务反馈、自定义角色，或插件、定时调度和角色控制。
这不证明它们缺少某项能力，也不证明本项目存在未经竞争的市场空位。来源与取舍见
[研究记录](references.md#桌面智能体深度研究与路线修订2026-09-20)。

| 拟建立的价值 | 用户应能感受到什么 | 验证办法 / 不足时的取舍 |
| --- | --- | --- |
| 持续的个人助手 | 不管理工作区和 Session，也能连续委托、接收提醒和找回结果 | 先让开发者在多个工作时段持续自用，处理连接与交付摩擦；普通用户留存后续再研究 |
| 3D 情境表达 | 朝向、注视、姿态和移动因上下文变化，小尺寸下仍看得懂 | 在实际桌面比例观看触发与反应；不能只以放大的模型检视器或动画数量过关 |
| 轻量桌面与独立道具 | 角色对桌面边缘/前台变化有反应，纸飞机可以离体飞行并返回 | 先看环境反应和道具生命周期是否成立；后续再验证真实任务的窗口关联，不假装已理解窗口内容 |
| 恰当的存在感 | 安静与活跃行为有变化，鼠标互动有回应，工作/审批仍可靠 | 开发者自用记录重复感、输入干扰和资源成本；不要求先完成一周普通用户留存验证 |
| 框架与角色解耦 | 同一意图能由不同身体表达，换角色不丢对话或改变权限 | 先用第二种显著不同的身体验证，再决定公开 SDK，而非先定义庞大标准 |

角色的审美、陪伴和个性本身也是当前探索价值。早期允许为演示与开发者兴趣探索不同表达，
不以尚无普通用户留存证据否定它们；长期市场验证留待可用且有特色的版本形成后。
不要求证明 3D 普遍优于 2D；需要证明本产品用到了 3D 的连续朝向、骨骼组合与空间交互，
并让演示和日常使用能看见这些区别；持续测量资源成本，但不预先要求证明市场竞争优势。

## 近期：可用性收尾与表现力验证相邻推进

| 增量 | 交付重点 | 通过标准 |
| --- | --- | --- |
| A：pre-release 收尾 | 结果打开/另存为；真实外部工具接入；首次连接/安装；通知、角色交互与常驻成本 | 用户能独立完成一次材料输入→必要决定→结果取得；尚未覆盖的平台/硬件明确记录 |
| B：桌面与交互最小框架 | Desktop/Dock/ActiveWindow；六套待机（四静两动）、鼠标/拖动/工作响应、本地调度、独立纸飞机 | 开发者能持续自用；实际演示看见情境转向、待机变化和道具离体飞行/回收；交互可靠 |
| C：更深入的空间行为 | 角色靠近/跟随/返回窗口；显式任务关联、失效回退与结果交付 | 通过 B 的基本概念扩展，不重建基础数据模型；不误导工作位置、不抢焦点；动作结果可回报 Agent |

A 保证可用，B 是当前探索与演示的重点，两者相邻推进；不要求完成所有发行验收才启动 B。
C 在 B 的基础骨架和道具/动作路径成立后扩展。基础桌面概念和纸飞机运动不再等到 C。
工程预览可以先交付 A；体现本产品方向的宣传演示需要完整 B。只有 C 的对应真实场景完成，
才声称具备任务/窗口的空间关联；复杂理解不是 B 或早期预览的门槛。

B 做一段 30–60 秒真实桌面演示：安静待机→鼠标接近/回应→活跃动作与纸飞机离体飞行→
工作/提醒→飞机回收。日常使用由本地随机和冷却控制，演示可加速触发但走同一动作路径。
开发者自用与演示验收见[桌面概念与交互基线](desktop-behavior.md)，不以静态模型预览替代。
C 再选「窗口陪伴」和「结果交付」，不同时铺开多个应用和多角色团队。

2026-09-20 制作路线调整：保留当前小爱和人偶原型，优先使用官方基础网格、成熟绑定/动作工具，
建立有限 Q 版体型模板，再精修小爱。模板先用自然跑步、抬手与宽袖代理验证，避免反复在成品外观上
修补运动基础。动作自然度优先于面部/发丝的最终精度；不改变 B 的产品目标，不先建设通用重定向平台。
选型、实际核查与剩余验证见[资产制作边界](character-assets.md)。

当前模型没有完整眼部/眨眼和手指能力；先核对现有骨架，使用头部/身体转向等可实现方式，
缺失能力明确回退。新动作需求在[动作交付清单](character-actions.md)对齐后交给人物会话。
六套待机是初始设计基线，不是当前已交付数量；行为可由 clips、局部层和道具轨迹组合。
纸飞机的独立运动在 B 接入，角色本体的窗口间行走在 C 扩展，不以滑动静态站姿假装走路。

## 框架现在定边界，随场景实现

详细职责与计划中的动作回执见[架构边界](architecture.md#planned-embodied-behavior-boundaries-2026-09-20)。

- **事实来源**：后端提供工作/审批/结果事实；原生宿主提供几何、显示与输入事实。
- **桌面上下文**：从 Desktop、Dock、ActiveWindow、Pointer 的最小快照开始，记录来源和有效期。
  环境反应不要求先建立任务关联；前台窗口只说明用户上下文，不证明 Agent 在其中工作。
  桌面世界数据与 Three.js 场景树分离，缺失几何允许 unknown/estimated。
- **行为调度**：Agent 提出高层意图，本地规则安排时机、优先级、冷却、打断与回落；
  空闲动作不调用模型，不新增永久运行的推理 Session。
- **动作执行**：原生宿主拥有屏幕位置和输入，角色播放器拥有局部骨骼、动画混合与姿态。
  不把逐帧鼠标/窗口移动交给 LLM，不重引入已修复的双窗拖动追赶。
- **实体与道具**：Actor 和 Prop 分离；纸飞机有挂点、独立轨迹与回收生命周期，默认点击穿透。
  角色包可以含身体与道具多个资产；道具不对应额外 Agent/Thread。
- **能力声明**：角色包描述待机组/权重/冷却、交互响应、骨架、道具挂点和回退；模型资产不执行脚本。
  角色表达不能批准请求、伪造完成或扩张工具权限。

先在现有 Wails/Go + React/TypeScript + Three.js、Blender → GLB 技术栈增量实现。
不为路线文档预先搭通用引擎、公共协议、全屏覆盖层或大型插件框架。

## 中长期

1. **持续身份与个人上下文**：可查看/修改的偏好、约定、提醒与工作恢复；逐步验证记忆需求。
   Bot 身份不依赖某个工作 Thread、cwd 或角色存活，模型仍按用户 prompt/定时任务等明确激活源运行。
2. **桌面语义与行为扩展**：在有限窗口关系之后，按具体场景加入有授权的 Accessibility/应用适配，
   视觉只补不足。读取窗口几何、读取内容、截图和控制其他应用分别定义能力；不默认持续录屏。
3. **多角色与多后端**：先以不同身体验证能力回退和动作表达，再以 Caelis 验证后端独立性。
   公共 SDK、角色安装、VRM、行为包和创作者生态以这些验证为前提；多角色协作是可选探索。

Codex App Server 仍是第一后端：发现用户本机服务/CLI、标准握手，不捆绑运行时，不锁用户发行版本。
macOS 完整发行后才实现 Windows；Linux 暂不列入计划。早期预览按既定边界使用 ad-hoc 包，
Developer ID/公证后置；角色公开分发授权单独确认，不由仓库代码许可替代。

## 与既有阶段计划的关系

保留 P0–P5 编号，避免把研究中的同名阶段当作本仓库任务编号。
P0/P1 是工具链与宿主，P2 是真实后端，P3 是普通用户可用性；A 对应现有 P1/P2 剩余验收与 P3 收尾。
P4 为「角色表现与桌面行为」：P4.1 接入已有资产；P4.2 对应 B，包含基础世界/交互/道具；
P4.3 对应 C，扩展角色位移与任务关联；P4.4 才推进角色扩展。
P5 为后续 Caelis 适配；不阻塞 B/C，也不以新后端替换尚未验证的产品体验。
执行项见[实现计划](implementation-plan.md)，发布缺口见[MVP 清单](mvp-checklist.md)，
最新实现/实测与当前授权范围见[交接](handoff.md)和[准备记录](preparation-status.md)。

## 验证纪律

稳定协议尊重既有 schema 与有意义的契约测试，不重复遍历所有版本与极端组合。
真实验证集中在动作观感、OS 输入/焦点、几何/命中协调、常驻成本和不确定的外部集成。
动作到达桥接、片段能播放、真实鼠标可用、开发者自用和演示表现分别记录，不互相代替。
性能在相同机器和显示条件下对比，优先事件驱动和局部更新，不先承诺未经测量的帧率/功耗。
早期反馈可通过本机观察和访谈完成，不为验证路线默认上传桌面、聊天或行为遥测。
