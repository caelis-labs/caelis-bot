# Caelis Bot 首版可用性评估

评估日期：2026-09-23。代码基线：`8db8611`。这是评估与建议，不表示下述缺口已经实现。

后续决策：用户将 Bot 自有长期记忆提升为本次 release 核心，并要求产品能力从 Caelis Core
上移到 Bot。实施顺序以 [Bot 产品宿主规划](bot-platform-architecture.md) 为准；
下文的现状证据仍有效，原建议顺序仅作为本次架构调整前的评估记录。

## 判断

目前适合开发者自用和受控预览，尚不适合宣称普通用户在两个 Runtime 下都能独立完成日常委托。
桌面入口、对话、审批、任务委派和运行时配置已经形成骨架；首版最大的缺口是材料输入、后台工作、
结果交付和故障恢复之间的连续体验。继续增加工具数量或角色动作，不能替代这条路径。

Codex 路径更接近可用的开发者预览。Caelis 的兼容开发构建已具备适配实现和先前真实模型联调记录，
但本轮核实的公开最新版仍为 [v0.60.1](https://github.com/caelis-labs/caelis/releases/tag/v0.60.1)，
本机安装也是该版本，实际设置页禁用切换。因此“开发版可联调”和“新用户可下载安装使用”必须分开。

不要求两套 Runtime 功能完全相同；要求核心委托流程一致，差异在选择或操作之前说明。
用户始终面对一个 Bot，后台工作可以多项并行，但不需要管理内部 Session 或 Thread。

## 证据范围

- 本轮：阅读当前实现、契约和准备记录；检查实际 macOS 设置页的 Codex、Caelis、模型与权限入口；
  核实本机版本和 GitHub 最新 Caelis release。没有切换运行时、安装软件、修改登录或发送模型请求。
- 当前运行进程沿用本轮内容包提交前已加载的版本；设置页观察不用于证明新内容包界面已在日常进程生效。
- 先前验证：`docs/preparation-status.md` 记录 Codex 独立任务联调，以及
  `xiaomi/mimo-v2.6-flash` 的聊天、并行工作、审批、汇报、提醒和重启恢复验收。本轮没有重跑这些验收。
- 未验证：干净机器首次登录、日常真实文档制作、真实外部连接器、长时常驻、硬件睡眠、多屏、完整无障碍。
  不给出未经测量的成功率或响应时间。
- 旧 `mvp-checklist.md` 仍含“Caelis adapter 暂不推进”等历史范围，不能作为当前能力清单。

## 当前能力对照

下表 Caelis 一栏指满足 `docs/caelis-integration.md` 能力握手的构建，**不包括公开 0.60.1**。

| 用户要做的事 | Codex Runtime | Caelis Runtime | 可用性判断 |
| --- | --- | --- | --- |
| 安装、连接、切换 | 自动发现/自选 CLI，显式安装，ChatGPT/API Key 连接 | 自动发现/自选 CLI，官方安装更新、服务检测/启动、连接模型 | 引导和管理入口已做；完整干净安装验收未完成，Caelis 缺兼容公开发行版 |
| 选择模型与权限 | 模型、effort、速度、审批模式 | 模型目录和 Bot 专属配置；effort/Fast 按模型能力展示，受限工作区策略 | 不应把 Codex 的审批模式照搬到 Caelis；模型和凭据由各 Runtime 管理 |
| 持续聊天 | 流式回复、Markdown、历史恢复/分页、停止和运行中补充 | 流式回复、恢复最近 64 turns、停止；主 Bot 不支持运行中补充 | 两者对话独立；Caelis 尚缺更早历史分页 |
| 提供材料 | 图片与普通文件副本，最多 8 个、单个 20 MB；引用已发现技能/插件 | 文本；协商支持后最多 4 张图片、单张 8 MiB；不接受任意文件或引用 ID | 选择器仍按通用的 8 个/20 MB 放行，Caelis 会到发送时才拒绝不支持的材料 |
| 委派专业工作 | 创建/读/续写/停止 Bot 自有任务；独立目录，最多 3 个未结束任务 | Control 原生的自有工作创建、读取、继续/补充/中断，适配器观察 | 秘书层成立；都不是任意 Codex App 任务管理器，也未接入用户已有项目 |
| 必要授权和后台汇报 | 原生审批、自动审查状态、完成后有限汇报激活 | 保留各工作原生审批选项，Control 汇报及 completion 确认 | 已有可靠性基础；没有完整的、可直接操控的后台任务展示 |
| 取得文件成果 | 主对话识别的产物可在访达中显示 | 当前是文本结果，无产物下载适配 | 独立任务文件回传未贯通；没有完整“打开/另存为”闭环 |
| 提醒和定时委托 | 单次/间隔/每日，持久调度，聊天中管理 | Control 授权提醒，Bot 计时触发和呈现 | 已有能力；还缺无需模型也能核对、暂停、取消的简洁入口和硬件送达验收 |
| 使用外部能力 | 原生工具发现、技能引用及部分连接授权 | 取决于 Caelis 配置；Bot 未提供等价技能引用与完整连接器管理 | 不能等同于 Codex App 当前会话的全部插件工具；缺代表性真实外部工作流验收 |
| 长期个人上下文 | Bot 身份、历史、提醒持久化 | Control Bot 身份、历史及原生私有空间 | 尚无统一、用户可查看/更正/删除的个人记忆能力；历史保留不等于长期记忆 |

共用产品层已有：菜单栏常驻、快捷输入、聊天与审批、原生窗口唤回、通知入口、3D 桌宠和本地行为、
预置外观及第三方内容包导入。换外观不改变任务或授权。Windows 原生发行仍未实现。
读取桌面几何不等于理解屏幕内容，也不等于能够操控所有应用。

运行时切换需要就绪状态和重启，工作/审批/未知结果会阻止切换；独立保存对话和运行时设置是正确边界。
明确退出应用会结束当前客户端工作，不承诺退出后仍执行提醒或任务；隐藏角色、关闭面板则不等于退出。

## 需要优先解决的具体问题

### 1. P0：Caelis 首次接入没有可用的公开下载终点

实际设置页显示 0.60.1、禁用“切换至 Caelis”，与能力检测一致。当前保护是正确的，
不能为了让按钮可点而绕过握手。但新用户“安装最新版”后仍可能无法继续。

先发布兼容 Runtime，再以真正的发行包验收“发现或安装 → 启动服务 → 配模型 → 首条回复”。
二进制更新与正在运行的 Host 更新必须区分；共享 Host 的重启需要可理解的显式处理。

证据：`docs/caelis-integration.md`；`frontend/src/RuntimeSettings.tsx`；本轮界面步骤 2。

### 2. P0：专业工作完成后，用户可能拿不到文件

`api.Task` 目前只有字符串 `Result`，没有结构化产物列表。Codex 工作目录位于 `Tasks/<id>`，
主聊天从 Markdown 提取文件时只接纳主 `Work` 目录下的链接；任务观察只截取助手正文。
因此工作任务给出路径，不会自然形成聊天中的可靠文件操作。不能把模型偶尔复制文件当成交付契约。
Caelis 则明确没有任意文件上传或产物下载能力。

应由原生层登记材料和产物句柄、归属和可访问性，适配器保留各自权限；UI 提供打开、另存为和重新定位。
材料的类型/数量/大小由能力决定，选择时就解释限制，避免用户写完提示再失败。

证据：`internal/backend/api/tasks.go`；`internal/backend/codex/tasks.go`；
`internal/backend/codex/projection.go`；`internal/backend/caelis/commands.go`；
`internal/desktop/attachments.go`；`internal/backend/service.go`；`frontend/src/Panel.tsx`。

### 3. P0：后台任务的事实与控制尚未充分到达用户界面

模型能读/停任务，不等于用户随时看得见、停得掉。公共 Snapshot 没有结构化任务列表；
Caelis 的停止状态主要跟随秘书主回合。秘书空闲、工作仍在后台运行时，不能依赖用户再发一句话，
等待一次模型调用才能确认进度或取消工作。

在对话中放精简任务卡：标题、运行/等待授权/完成/失败、停止或继续、结果入口。
卡片读取真实状态，按钮作用于确定的自有任务；不暴露 Thread ID、工作区树或任务控制台。
完成通知须能回到具体结果，并允许用户处理一个审批时继续与秘书交流。

证据：`internal/backend/api/contract.go`、`tasks.go`；
`internal/backend/caelis/projection.go`；`frontend/src/Panel.tsx`、`chat-presentation.ts`。

### 4. P0：安全保留“未知”之后，还需要用户走得通的恢复路径

不自动重发是正确底线。Caelis 当前的部分配置、审批、中断和确认回执丢失后可能长期待核对；
`recoverPrompts` 主要核对 prompt，界面通用“重新连接”无法保证解决全部操作。
聊天连接文案仍硬编码 Codex，Caelis 用户在恢复时可能被误导。

需要区分“正在核对”“需重新登录”“需重启服务”“无法确认，需明确重新授权”，提供相应动作，
保留草稿和原任务。不能用清空记录、生成新 ID 或模型猜测成功来解锁。

证据：`internal/backend/caelis/projection.go`、`commands.go`；
`docs/caelis-integration.md` 的恢复限制；`frontend/src/Panel.tsx:234`。

### 5. P1：持续使用的容量和提醒管理还不完整

Codex 达到 100 条任务记录后会拒绝创建，而目前没有任务归档/回收路径；
Caelis 的工作/完成列表也没有分页归档。Caelis 历史仅恢复最近 64 turns。
提醒可以通过模型工具管理，但模型服务断线时，用户仍应能核对下次时间、暂停或取消。

补充原生可控的提醒摘要与任务保留策略；归档不能删除执行回执或破坏去重。
为单次、每日、时区、睡眠补发和退出暂停提供简短、准确的回执。
这里需要持续性功能，不需要新增多级导航。

证据：`internal/backend/codex/tasks.go:127`；`internal/bot/runtime.go`；
`docs/bot-design.md`；`docs/caelis-integration.md`。

## 首个“好用版本”的最小承诺

建议明确为：**一个能随手委托、后台办事、可靠交付和提醒的 macOS 个人助手。**
先支持两三类真实高频工作，不宣传未验收的全能电脑控制。

| 最小能力 | 首版验收 |
| --- | --- |
| 用户能自己接通 | 干净用户从安装 Bot 开始，在所选 Runtime 下走完安装/登录或模型连接，获得首条回复；失败和取消可回退，不查终端日志 |
| 材料能进入工作 | 选择一份受支持文档/数据或图片，能力不足在发送前说明；工作只获得明确提供的材料和权限 |
| 委托后可继续聊天 | 专业任务独立执行；同时交代第二件事仍可用；审批、停止、完成均对应正确任务 |
| 结果能拿到并继续改 | 生成一个真实文件，聊天可打开/另存为；重启后仍可找回；“按刚才结果修改”能继续原工作 |
| 出问题不会重复执行 | 断网、Host 重启、登录失效和丢失回执可解释、可恢复；保留草稿，不重复命令、审批或提醒 |
| 提醒说到做到 | 明确下次时间和常驻前提；可核对/取消；真实睡眠唤醒、通知点击返回、退出后再次打开有确定结果 |
| 桌面上不添乱 | 输入响应、IME、拖动、双击、多屏/Space、隐藏/关闭与退出语义通过原生验收；观察一个完整工作日的资源使用 |

已完成的视觉和内容包能力保留；首版只需预置资源和第三方包导入稳定可用。
无需以更多角色数量、语音、通用屏幕控制或 Windows 发行作为本轮最低门槛。
根据后续产品决定，私人 Notebook 与可查看、更正、忘记的长期记忆已提升为本轮核心，
由 Bot 通过嵌入 Memory 实现；自动人格学习与持续后台整理不在最低范围。

如首版宣传“直接修改已有代码项目”，用户选择目录、权限授予和 Git worktree 隔离必须提升为 P0；
否则首版应明确以用户提供材料和独立工作目录交付为范围，已有项目接入后续单独实现。

## 建议实施切片

每片独立提交、独立验收；这是建议顺序，尚未实施。

1. **接入与能力提示收口**：兼容 Caelis Runtime 公开发行配合；Bot 的 setup、恢复文案和附件预检。
   落点：`internal/app/setup.go`、`internal/backend/api/setup.go`、各 adapter 的 `setup.go`、
   `internal/desktop/attachments.go`、`frontend/src/RuntimeSettings.tsx`、`Panel.tsx`。
   验收：两套真实发行 Runtime 的全新接入，以及不支持附件的提前反馈；不静默改用其他 Runtime。
2. **材料与产物交付契约**：输入句柄、任务成果列表、打开/另存为及失效反馈。
   落点：`internal/backend/api/tasks.go`、`capabilities.go`、两套 adapter、原生文件服务、聊天结果展示；
   Caelis 缺少的公开能力由 Caelis Control 实现，Bot 不绕过权限直接读取 Store。
   验收：两边各完成“提供文件 → 独立工作 → 实际打开结果 → 重启找回 → 继续修改”。
3. **任务状态与恢复**：对话任务卡、确定目标的停止/继续、各类未知操作对账与可操作修复。
   落点：公共 Snapshot、两套 adapter 的任务/恢复代码、`internal/backend/service.go`、`frontend/src/Panel.tsx`。
   验收：两个并行任务、一个等待审批；秘书仍能回复；单独停止另一个任务；断线后不重复执行。
4. **持续使用与发行收尾**：任务归档、历史分页、提醒摘要/暂停取消、真实通知与常驻验收。
   落点：两套 adapter 的历史和任务边界、`internal/bot`、`internal/desktop/notifications.go`、上下文式提醒 UI。
   验收：超过现有容量仍可新建工作；归档后回执不丢；睡眠/退出/重启提醒行为与文案一致。
   普通用户完整 macOS 发行另需签名、公证、安装升级验收；目前待办签名工作不能算已完成。

真实业务验收选三项：从用户材料生成可保存的摘要/表格；两项并行委托及一项审批/取消；
一个次日提醒并继续昨日工作。若要宣传联网调研或外部应用处理，另选一个明确工具/连接器，
走完发现、授权、调用、失效恢复，不能以裸命令 smoke 代替。

## 本轮界面观察

本地截图存于 `.cache/usability-review-20260923/`，只包含设置页面，不含聊天正文或凭据。
对应的 `ui-audit.md` 按以下步骤保留截图和说明：

1. Codex 运行时：能识别实际 CLI，连接、账号和模型分组清楚。管理页与“模型与权限”存在两个模型入口，
   生效方式应统一且说清，无需新增配置解释段落。
2. Caelis 运行时：管理对象与“当前使用”分开，禁用切换和原因符合真实能力。当前没有可用公开升级终点，
   属于发行与能力问题，不应通过美化禁用按钮解决。
3. 模型与权限：控件高度、分组、内聚短注释已经改善；原生 AX 暴露了名称、值和禁用原因。
   尚未完成 VoiceOver、完整键盘遍历和对比度测量，不能据此宣称无障碍合规。

这些观察不能证明首次引导、真实任务流或长期运行均已通过。评估不改变当前运行时、凭据或权限。
